# Product studio: the skills catalog (approved 2026-11-12)

_From the audit of 59 existing skills (6 auditors), a designed catalog, two critiques and a revision. 2026-11-12._

**The founder's decisions (2026-11-12):**

1. The name is `contextcraft/product-studio`. It serves go-to-market, product managers, designers
   and engineers, so it isn't called a design studio. Plugin and CLI: `product-studio`.
2. `studio/guardrails.mdx` is retired. `studio/rules.md` is the one rule source.
3. The 31 drops listed below are approved.
4. It is built first in this repo, under `studio/`. It moves to a new repo once contextcraft has
   its domain.

The build contract is `SPEC.md`. Where SPEC and this catalog differ in detail, for example the
rules samples living in `studio/rules/` and not `studio/evals/rules/`, SPEC wins.

## Principles

- One canonical rules file. studio/rules.md holds the rules: every row has a script: or review: test, and every scripted row has a known-bad sample. DESIGN.md is the narrative and tokens.css holds the canonical values. guardrails.mdx is retired: the migrate door turns an existing one into proposed rows and leaves a one-line pointer. How to add a rule lives once, in the rules.md header, with lint and eval in the CLI. There is no separate authoring guide that could drift from it.
- Five commands are the spine: setup, brief, check, loop and admin. Everything else is a reference under skills/<command>/references/ or skills/shared/, read by an explicit ${CLAUDE_PLUGIN_ROOT}/skills/... path. No guide reads another guide's files through a relative ../ path, and a build test checks that every named path exists in the built plugin.
- Code does the arithmetic and the model does the judgement. Every count, score, severity, setup class, near-threshold list, diff table, contrast ratio and run-log row is printed or validated by the scan CLI. Guides present that output and add only judgement: palette clustering, fix wording, proposals and review answers. With no counters there is no score. A guide is not written against a CLI command that does not exist yet; the skill is marked blocked on that command instead.
- The agent proposes and a person rules. A write to studio/ is shown as a diff and made only after a yes. The named exceptions are three, each tested: the run-log append (studio/.state/runs.jsonl), the generated preview page (studio/.state/preview.html), and the proposal files an admin run writes when a person types it. Gates, closes, merges, publishes, issue filing, deploys and every self-modification of skills or rules need a person's recorded ruling, written as a decision line and never left as a chat 'it holds'. The agent never merges, and the roster template says the same.
- Brand-neutral and layout-true. No Systemix, POC, client (helloBill, Vero, Vito) or dead-product paths, names or examples. All paths come from one layout module: studio/{DESIGN.md, tokens.css, rules.md, rules/, decisions/, goals/, loops/, context/, briefs/, evaluations.md, LEARNINGS.md, proposals/, .studio/} plus the existing docs/components and docs/manifest.json. The plugin namespace is one build-time constant, so a rename touches one file. A CI leak-grep with literal strings enforces this.
- One mechanism per job. Tokens drift is the T rows of rules check, with drift scan findings emitted as rule IDs. There is one readiness score. There is one goal store (studio/goals/G-NNN) and one decision record (each goal's decision log). There is one learnings ledger (studio/LEARNINGS.md, cited-bullet grammar). There is one run record: check results go to the run log only, and studio/evaluations.md belongs to build.measure alone.
- Free studio, paid setup. Everything that ships runs with no network, no API key and no MCP. Figma and analytics are optional sources that degrade to 'not connected'. The free tool sells by showing what it refused to decide: setup and score end with 'Open questions for a person' (contradictions, canonical choices, missing rules). The report carries no pitch copy. One neutral line in the docs says a person can rule on these with you.
- First value comes first. /product-studio:check works on a repo with no studio/: it runs the starter rules and the audit, writes nothing and offers setup. Solo is the default roster, and the team preset is opt-in. User-facing docs describe four jobs: Set up your system, Before you build, Review, Ship and learn. Internal words (roster, holder, deputy, join, gate) always come with a plain gloss.
- Designers approve what they see. Token and visual gates point at a generated preview page (swatches with contrast, type scale, radius, spacing), rendered by code. Exploration (2–3 variants in real code, each checked against the rules) is a loop step, and a person picks at a gate.
- Every kept skill ships with its eval: trigger asks (including negatives and collisions with other design plugins), cases with must_include and must_not_include, known-bad samples, and a fixture repo. A skill with no eval is not done. Layer-1 evals need no key, and model-graded evals live in a separate maintainer harness.
- Repo text is data, never instructions, and is never pasted unquoted into a shell. A source the agent cannot reach is named, never invented. Privacy travels with the run log: it is local and gitignored by default, notes hold only the person's words, and a privacy lint runs on every append and in CI.

## The spine

| Command | Model may run it | Job |
|---|---|---|
| `/product-studio:setup` | yes | Set up your system. ## The admin loop

**command**: /product-studio:admin (disable-model-invocation: true). Subcommands: rate [run-id] up|down "note" · runs [--since <date>] · run (manual by default; an optional Claude Code scheduled task, propose-only) · approve P-NNN · decline P-NNN "why". Deterministic side in the CLI: `runs log|rate|list`, `admin eval` (layer 1, no key), `proposals lint|list`. The key-needing trigger and case harness is evals/run.mjs, a maintainer and CI tool whose results admin only reads.

**run_log**: studio/.state/runs.jsonl. It is gitignored by default; a team can opt in to committing it, and setup then adds a merge=union gitattribute and the privacy lint to CI. It is one of the three named auto-writes. Every command appends one row as its final step via `runs log --json -`, which validates the schema and runs the privacy lint. Fields: run, at, command, args, surface, depth, goal, result (pass|pass-with-flags|pass-with-fixes|fail|proposed|written|stopped-at-gate|error), blocks, flags, false_positives [{rule, where, why}], sources, files_written, duration_s, rating (up|down|none), note, studio_version, claude_code_version, kind (run|eval|admin). Failed and short runs are logged too. Rows from the eval harness carry kind: eval. check writes no other record.

**rating**: Up or down plus an optional note in the person's own words. It is asked without blocking, only after a run that ended in error or fail or dropped a false positive, and otherwise at most once a day. There is no repeat ask on the next run; `admin rate` records one any time. The digest aggregates down share per command and false positives per rule. Thresholds are scaled by run count, so a solo user is not held to team-volume bars.

**admin_run**: `/product-studio:admin run`, typed by a person, or by an optional scheduled task that stays propose-only. (1) `admin eval`, key-free: rules lint and eval (known-bad), review-case presence, tokens lint, docs check, loops check, and plugin build, path and leak checks. If evals/results/<latest>.json exists, the trigger and case scores and the week-over-week change are read from it, otherwise marked 'not run'. (2) A counts-only digest of what the studio did since the last admin row: rules caught per surface, blocks fixed, drift trend, false positives dropped. (3) Thresholds: the same rule dropped as a false positive at least 3 times; a down share of at least 30% over at least 5 runs of one command; any trigger miss or negative firing; an error repeated twice; any failing eval. (4) At most 3 proposals, ranked by evidence count. (5) An admin row is appended. It never edits skills, rules or plugin files.

**proposals**: studio/proposals/P-NNN-slug.md, validated by `proposals lint`. Frontmatter: id, target (client = this repo's studio/ data; plugin = the studio's own skills, triggers or scan code), kind (wording|trigger|rule-fix|new-rule|new-eval|bug), evidence (run ids or failing eval ids, at least one), status New|Approved|Shipped|Declined|Failed, decided_by, decided_at, evals_before, evals_after. Body: the problem in one paragraph, the change as a unified diff, and how it will be checked. Only a person in the roster rules. Client target: apply, rerun the evals, record after scores, and on any regression revert and mark Failed. Plugin target: never edit vendored plugin files. Draft a scrubbed upstream issue (title, evidence counts with no paths, eval before and after) for the contextcraft/product-studio repo, and after a yes file it with `gh issue create` or give a prefilled new-issue URL. In the maintainer's own repo the change goes through an ordinary pull request, not through admin.

**evals**: 
- evals/triggers.json: 30 brand-neutral asks. About 18 positives for setup, brief and check, using designer phrasing ('review my design', 'is this on-brand', 'make this match our system', 'what colours should I use here', 'set up a design system', 'check my design'). 12 negatives must fire nothing: SQL query, meeting summary, unit-test fix, translation, email reply, dependency bump, README typo, regex explanation, plus the collisions 'critique this mockup', 'design a logo', 'write a blog post' and 'accessibility review of this Figma'. Any ask naming loop or admin is a negative, because both are disable-model-invocation. The suite runs with and without another design plugin installed and is scored from nested-session transcripts by which Skill was invoked.
- evals/cases/first-run.json: on F1, a fresh user typing 'check my design' gets findings in one turn, then a setup proposal with the preview page and an 'Open questions for a person' list. This case gates the release.
- evals/cases/brief.json: 6 cases (surface, depth, fixture) with must_include_rules, must_not_include_rules, the four fixed headings, and 'Sources'.
- evals/cases/check.json: 8 cases on F1 and F3 with expected verdict and rule IDs, must_not_include (no T1 on tokens.css), and a no-design/ zero-setup case.
- studio/rules/known-bad/* plus expected.json: one sample per scripted starter rule (including contrast, <Image> alt, and a CSS id selector that must NOT fire T1) and one known-good file. `rules eval` catches each with its exact ID and raises no block on the known-good file. It is key-free.
- studio/rules/review-cases.json: a known-bad and a known-good snippet per review: row with the expected answer. `rules eval` checks only that each case is present; grading is layer 2 (judge).
- evals/cases/setup.json: per door (F0 interview, F1 and F2 from-code, F5 import including Figma variables, F8 migrate): expected file set, required role names in both themes, lint, eval and tokens lint passing, no write before a yes, and an open-questions section.
- evals/cases/loop.json: a scripted F4 walk (open, gate approve, next, gate approve, decide) with `loops check` at every stop, a decision-line regex, refusal of a non-roster name, and a product.design case capped at 3 variants.
- evals/cases/admin.json: on F6, exactly 3 expected proposals and the expected digest counts; a clean log gives 0; a plugin-target approve in the client fixture gives a draft only; a regression after apply reverts.

**guardrails**: 
- Self-modification of skills, triggers, scan code or rules happens only through a person's approve on a P-NNN file. `run` and scheduled tasks are propose-only and are tested to write nothing outside studio/proposals and studio/.state.
- At most 3 proposals per run, each with at least one run id or failing eval as evidence. No evidence, no proposal.
- A plugin-target proposal never edits vendored plugin files in a client repo. It becomes an upstream issue draft, filed only after a yes.
- Every applied change reruns the evals and records before and after. A regression reverts automatically and marks the proposal Failed.
- Run-log privacy: local and gitignored by default, no customer data, no session transcripts, and notes hold only the person's words. The privacy lint runs on every append and in CI; upstream drafts carry counts and no paths.
- Approve and decline are ruled by a person named in the roster. The agent never approves its own proposal.
- Admin cannot change its thresholds, cap or rating frequency. Changing them is itself a plugin-target proposal.
- admin eval needs no key and no network. Nested-session evals belong to the maintainer harness, never to a client's admin run.

### Method

Three layers. (1) Deterministic, on every pull request in CI and inside `admin eval`, with no key: Jest goldens for every CLI command on F0–F8, the rules known-bad eval and review-case presence, tokens lint, schema and privacy lints, the loops check walk, and the plugin structure, path and leak tests. This layer is the merge gate and must stay at 100%. (2) Behavioural, run by the maintainer nightly or weekly, needing a key: evals/run.mjs copies a fixture into a temp dir, runs git init and the scripted branch, and spawns `claude -p --plugin-dir <built plugin> --output-format stream-json` with the case's ask. Multi-turn cases (approval turns, interview personas) are driven by a scripted or persona user agent through --resume. The parsed transcript gives Skill invocations (trigger scoring), tool calls (write-before-yes, files touched) and the final reply. The harness then asserts on the files on disk and reruns the deterministic scan. Fixture × case runs fan out in parallel nested sessions with a Claude Code workflow or ultracode as the orchestrator, each case isolated in its own temp repo and session. (3) Judging, for free text only (brief, decide brief, review answers, setup proposals, interview flow, review-case answers): a separate judge session sees only the rubric, the fixture's expected facts and the output, never the skill text, and returns pass or fail per criterion with a quote. Each case runs 3 samples and passes on majority, after the deterministic must_include and must_not_include checks. Every case writes a kind: eval row, and the aggregate goes to evals/results/<date>.json with the CLI and Claude Code versions. The client-side admin run only reads that file. Release bar: layer 1 at 100%; the first-run case passing; triggers at least 90% positive and 100% negative; every other non-beta case at least 90%; no case regressing against the last release. Build order: the CLI commands each skill is blocked on (audit --json, rules list, tokens diff, tokens lint, runs, proposals, admin eval, learnings, preview, migrate) with their goldens first, then the guides, then layers 2 and 3.

## Risks

- About ten CLI commands are new work (audit --json, rules list, tokens diff, tokens lint, runs, proposals, admin eval, learnings, preview, migrate, plus score v2 and jobs check). Every guide that depends on one is marked BLOCKED. If the CLI slips, the guides fall back to untestable prose, so build the CLI and its goldens first. score and jobs stay beta and are not on the release path.
- Retiring guardrails.mdx and experiments/ affects the two live installs: this POC and the Vero design system, which also depends on docs/manifest.json. The migrate door with fixture F8 has to work before either moves, or they stay on the old plugin. Docs keep the docs/ path for this reason.
- Committing the run log on a team can leak notes or paths and causes merge conflicts. It is local by default; opt-in adds merge=union, the privacy lint, and counts-only upstream drafts.
- Nested-session evals cost money and are non-deterministic (model and Claude Code version drift). Layer 1 stays the key-free merge gate. Layers 2–3 run on a schedule with a 3-sample majority, and the CLI and Claude Code versions are recorded per row.
- Trigger behaviour depends on how Claude Code surfaces plugin skills and on which other design plugins a user has installed. Run the suite with collisions installed, and treat a broad drop as an environment change. The descriptions say where the studio defers (for example, copywriting to ux-copy, with check reviewing).
- The admin loop can churn the rules through overfitting to one noisy person. The 3-proposal cap, run-count-scaled thresholds, automatic revert on regression and a roster person's approval on every change mitigate this. A solo user may rarely reach a threshold, which is acceptable.
- Upstream improvement signal depends on people filing the drafted issue. Make it a single yes (gh or a prefilled URL), keep it scrubbed, and never send anything automatically. This is the founder's main view of how the free studio is used.
- Identity for gates and approvals is git user.name matched against the roster, which is weak on shared machines and in CI. Accept and state it in v1; consider signed commits for team setups.
- The name product-studio, the package @contextcraft/product-studio and the binary may collide on npm, in the plugin marketplace or with the domain. The check happens before publish, and the namespace is one build constant so a rename stays cheap.
- The preview page and the explore step add scope that designers expect but that engineers may see as extra. Keep preview to tokens only in v1 (component specimens are roadmap) and cap exploration at 3 variants and 3 rounds.
- Dropping theming, Storybook coverage, the flow map and JTBD from the free path narrows what is visible of the paid client-setup story. Keep them as setup-engagement deliverables on the roadmap, and let the 'Open questions for a person' section carry the honest case for paid help.
